# i18n architecture — Phase 0 spec

Status: **awaiting sign-off**. Nothing in `src/` has been touched.

This document is the contract. Every later session implementing i18n reads this
first; if an implementation detail disagrees with this file, this file wins
until it is amended.

---

## 0. Scope

The goal is **the system, not the content**. Site copy is being rewritten
wholesale, so no existing copy gets extracted or translated. We build the
machinery, prove it on a thin slice, and the rewrite then authors new copy
directly into locale files — never into TSX.

Explicitly **out** of scope:

- Bulk extraction of current page copy (it is about to be deleted).
- Bulk translation of the six locales (nothing stable to translate yet).
- RTL support. Decided: never in scope. Physical CSS properties are fine.
- Per-market pricing, tax, or currency. USD only for v1.
- A TMS (Crowdin/Lokalise). Repo-based files until 3+ locales AND 2+ people.

## 2. Locales

```
en   (source of truth)
es
pt-br
de
fr
it
```

- `en` is authored. The other five are generated.
- All six are Latin-script. `Geist subsets: ["latin"]` already covers
  ä ö ü ß é è ç à ñ ã. **No font work required.**
- URL segments are lowercase BCP-47: `pt-br`, not `pt-BR`.
- One Portuguese and one Spanish, deliberately. `pt-PT` and `es-MX` visitors
  match down by tag fallback. If a regional variant is ever added, revisit
  §3 detection — that is the only case where country data starts to matter.

**Locale is not market.** Locale means language. If per-country pricing, VAT,
or availability ever lands, that is a separate `market` concept and must not be
folded into the locale segment.

## 3. URL structure & detection

### Prefix

`localePrefix: 'always'` (the next-intl default). **Every** locale is prefixed,
including English:

```
/en/apps/alt-text
/pt-br/apps/alt-text
/            → 307 → /{detected}
```

Rationale: the `as-needed` alternative special-cases the default locale in
every link helper, canonical tag, and sitemap entry forever, to save one path
segment. The site is currently `SITE_INDEXABLE=false` and unindexed, so
prefix-all costs nothing now and there is no redirect debt to inherit.

### Path segments are NOT translated

`/de/apps`, never `/de/anwendungen`. next-intl's `pathnames` option supports
localized slugs later; because all links go through the generated `Link` from
`createNavigation()`, adding them later is a config change, not a refactor.
No component may ever hardcode a path string.

### Navigation must stay in-locale

**Every internal link is locale-aware.** A visitor on `/de/apps` who clicks
"Blog" lands on `/de/blog`, never `/blog` or `/en/blog`. This is not optional
polish — a single raw `next/link` drops the visitor out of their language
mid-journey, and it will not show up in English testing.

`createNavigation(routing)` in `src/i18n/navigation.ts` exports drop-in,
locale-aware replacements:

| Import from `@/i18n/navigation` | Replaces                                                       |
| ------------------------------- | -------------------------------------------------------------- |
| `Link`                          | `next/link`                                                    |
| `redirect`, `permanentRedirect` | `next/navigation`                                              |
| `usePathname`, `useRouter`      | `next/navigation`                                              |
| `getPathname`                   | — (build a URL for a given locale; used by sitemap + switcher) |

Call sites are unchanged: `<Link href="/apps">` resolves against the active
locale automatically. An explicit `locale` prop forces a target locale — that
is how the language switcher works, and it is the **only** legitimate reason to
pass one.

`TrackedLink` wraps the localized `Link`, not `next/link`, so CTAs stay
in-locale too.

**Enforced by lint, not by discipline.** `no-restricted-imports` bans
`next/link` and the navigation exports of `next/navigation` outside
`src/i18n/`. Without the rule this decays the first time someone autocompletes
an import — and the failure is invisible unless you happen to be testing in
German.

### Detection precedence

1. **Explicit locale in the URL** — always wins, never overridden. A link
   shared into Slack must render identically for everyone.
2. **`NEXT_LOCALE` cookie** — the user's own switcher choice. Wins forever after.
3. **`Accept-Language`**, matched against the supported six.
4. **Country** — banner signal only. Never an auto-redirect.

1–3 are next-intl's built-in behaviour (`localeDetection: true`, default).
Set `localeCookie.maxAge` to one year; the default is session-only.

### Rules

- **Detection runs on bare `/` only.** Deep paths never redirect. Verify this
  holds for the built-in proxy during Phase 1 and pin it down if not.
- **Never auto-redirect on geo.** Browser `en` + IP `BR` keeps the visitor on
  English and shows a dismissible "Ver em português?" banner. Overriding a
  signal the user explicitly set is both a UX and an SEO wound.
- **`Vary: Accept-Language`** on the root redirect, or the CDN serves the first
  visitor's language to everybody.
- **Redirect in `proxy.ts`, never in a page.** A statically cached page cannot
  branch on request headers.
- **Do not cloak.** Googlebot sends no useful `Accept-Language` and crawls from
  US IPs, so it lands on `/en`. That is correct and consistent, provided
  `hreflang` advertises the other five.

Geo source: Vercel edge, free. Confirm the current API at implementation —
Next 15 removed `request.geo`; it is now either the `x-vercel-ip-country`
header or `geolocation()` from `@vercel/functions`.

## 4. Content tiers

The governing idea: **a page is a schema, a locale file fills it.** Templates
own layout and logic. Locale files own every word. Today `src/app/page.tsx`
mixes both across 209 lines; that must never recur.

| Tier              | Content                                                   | Location                        | Format                          |
| ----------------- | --------------------------------------------------------- | ------------------------------- | ------------------------------- |
| **1 — Chrome**    | nav, buttons, form labels, validation errors, aria-labels | `messages/{locale}/common.json` | ICU JSON                        |
| **2 — Page copy** | hero, section headings, FAQ, card copy, pricing labels    | `messages/{locale}/{page}.json` | ICU JSON, typed per-page schema |
| **3 — Documents** | privacy, terms, blog posts, changelog                     | `content/{locale}/{doc}.mdx`    | MDX                             |

### Why tier 3 is separate

Long-form prose does not belong in JSON strings, and more importantly a
locale's legal document must be allowed to **diverge, not merely translate** —
a Brazilian privacy page needs LGPD language, not a translated GDPR page. A
key-based system fights that; separate files do not.

Legal docs are translated-only for v1 (decided). The structure keeps the door
open at zero cost.

### Layout

```
messages/
  en/     common.json  home.json  apps.json  alt-text.json  …
  es/     …same key set
  pt-br/  …
  de/  fr/  it/
content/
  en/     privacy.mdx  support.mdx
  es/     …
src/i18n/
  routing.ts      defineRouting — locales, defaultLocale, localePrefix
  navigation.ts   createNavigation — Link, redirect, usePathname, useRouter
  request.ts      getRequestConfig — reads rootParams.locale()
src/proxy.ts      createMiddleware(routing)
src/app/[locale]/ every page, generateStaticParams over routing.locales
```

One namespace per file, matching the route. `useTranslations('home')` reads
`messages/{locale}/home.json`.

## 5. Key naming

- Keys are **stable ids, never the English text**. `hero.headline`, not
  `"The work your store needs done"`.
- Namespace mirrors the route: `home.*`, `altText.pricing.*`, `common.nav.*`.
- Lower camelCase segments, dot-nested. **No dashes** — ICU argument names
  reject them and consistency avoids the trap.
- Nest by section, not by component. Sections survive redesigns; components
  do not.
- Changing English _meaningfully_ does not rename the key — it invalidates the
  source hash (§8) and triggers regeneration.

## 6. Interpolation — ICU MessageFormat

Single braces, and the placeholder carries a **type**. This is the difference
from Liquid: Liquid interpolates an already-formatted string, ICU formats the
value at render time using the locale.

### Values and numbers

```json
"scanned": "We found {needsAttention, number} of {total, number} images missing alt text."
```

`MIRROR` passes raw integers. `en` → "1,847 of 3,102". `pt-br` → "1.847 de
3.102". `de` → "1.847 von 3.102". Nobody writes a separator anywhere.

> **Never pre-format.** If a translator sees a digit, a currency symbol, or a
> date separator in their file, something is wrong upstream.

### Plurals

```json
"appCount": "{count, plural, =0 {no apps} one {# app} other {# apps}}"
```

`#` renders the locale-formatted number. French treats 0 as singular; English
does not. The translator supplies the forms their language actually has, and
the call site stays `t('appCount', {count})` in every locale.

### Select

```json
"status": "{status, select, live {Live} lab {In the lab} other {Coming soon}}"
```

`other` is required.

### Rich text

The case that matters most for marketing prose — a sentence containing a bold
phrase or an inline link:

```json
"legal": "Read our <link>privacy policy</link> before you install."
```

Tags live in the message; components are supplied at the call site via
`t.rich('legal', { link: (chunks) => <Link href="/privacy">{chunks}</Link> })`.
Tags nest arbitrarily.

### Currency (USD-only v1)

```json
"price": "{amount, number, ::currency/USD}"
```

Still locale-formatted — `$29.00` in en, `29,00 $US` in fr — always USD. Pair
with a visible "billed in USD" line.

### Escaping

Literal braces wrap in single quotes: `"Use '{variable}' syntax"`.

### The one rule that matters most

> **One sentence = one key**, including its punctuation and inline markup.
> Never concatenate keys. Never wrap markup around a separate fragment key.

German and Italian punish fragment assembly immediately — word order moves and
the result is ungrammatical in ways invisible from the English side. This is
the single most common i18n defect and it is a discipline problem, not a
tooling one.

## 7. Translation workflow

All five non-English locales are **AI-generated, unreviewed** (decided). Two
consequences:

### The source hash is the pipeline, not a warning

Each translated key carries a hash of its English source. Edit English → CI
marks the five locales stale → `npm run i18n:sync` regenerates only the stale
keys. That is the entire translation pipeline, and it only works because keys
are stable ids with hashes attached.

### Positioning copy gets a stricter brief

~15 strings carry the positioning — hero, the product-truth lines, the
"written laws" framing. An unreviewed model smooths those into generic SaaS
voice and nobody notices, because nobody here reads Italian. Mark them
`"@critical": true` in the source file; the generator applies a stricter
prompt to those keys. Everything else ships unreviewed.

### Glossary + do-not-translate

`i18n/glossary.json`, shared with the Shopify app UI and the App Store listing
so the brand reads consistently across all three surfaces.

**Never translate:** Leaf, Leaf Digital, Shopify, Shopify Admin, App Store,
alt text, ChatGPT.

**Translate consistently (per-locale table):** "agentic shelf", "coverage",
"scan", "auto-pilot", "the mirror".

## 8. Guards — CI, from day one

These are the whole point. Without them the system decays within two months.

1. **Key parity.** Every locale carries exactly the `en` key set. A missing key
   fails the build. Never a silent English fallback — we do not ship
   half-Portuguese pages.
2. **Source-hash staleness.** Per §7. Stale keys fail CI; `i18n:sync` fixes.
3. **ESLint: no literal text in JSX.** The rule that actually prevents decay.
   Without it, month three has hardcoded English scattered through new
   components again.
4. **Quarantine list.** Every current page would trip rule 3, and we are not
   extracting them. Existing files go on an explicit ignore list, which shrinks
   to nothing as the content rewrite replaces each page. **The list doubles as
   the migration tracker: whatever remains on it has not been done.**
5. **Fallback policy.** Tiers 1 and 2: no fallback, fail the build. Tier 3
   documents: fall back to `en` with a visible notice, and omit that page from
   `hreflang` for the missing locale.

## 9. SEO

- `<html lang>` is dynamic. `dir` is always `ltr` (no RTL, ever).
- next-intl's proxy emits alternate-language `Link` **headers** including
  `x-default` automatically. Google accepts headers, but many SEO tools only
  inspect `<head>`. **Decision: also emit `<link rel="alternate">` tags via
  `generateMetadata().alternates.languages`.** Belt and braces; costs nothing.
- `sitemap.ts` becomes a locale × route matrix with per-entry `alternates`.
  Currently hardcodes five paths — it must derive from the same route source as
  the navigation helpers, not a second hand-maintained list.
- `opengraph-image.tsx` (root) and `apps/alt-text/opengraph-image.tsx` are
  monolingual today. Both take the locale param and pull strings from tier 1/2.
- Canonical per locale.
- `robots.ts` and `SITE_INDEXABLE` behaviour unchanged.

## 10. Thin slice

An unexercised system is a system you discover is wrong 40 pages into the
content rewrite. So one narrow path goes end-to-end through all three tiers in
all six locales:

- **Tier 1** — header + footer chrome. Shared, and it survives the rewrite.
- **Tier 2** — one page's sections. **Open: which page is least likely to be
  rewritten?** Maintainer picks.
- **Tier 3** — `privacy.mdx`, if legal copy is staying roughly as-is.

Small enough to be near-zero throwaway; complete enough to prove ICU
formatting, plurals, rich text, the sync script, hreflang, and the switcher
all work together.
